# InsureDrive GPS Tracking v1.6.0

## Architecture

InsureDrive does **not** use Gmail as a GPS source. A dedicated Google/Gmail
address may be saved as optional device-identification metadata only.

`Android car audio GPS -> Tracker Mode -> authenticated Edge Function -> Supabase -> Realtime -> Admin/Owner UI`

Each active vehicle can have one active tracking device. Each active device UID
can be paired with one vehicle. Pairing uses a short-lived code generated by an
Administrator. The backend returns a device secret once; only its SHA-256 hash
is stored in Supabase, while the raw secret is kept in Android secure storage.

## Included capabilities

- Dedicated car-audio/head-unit pairing and revocation
- Optional dedicated Google/Gmail email metadata; no Gmail passwords
- Android GPS latitude/longitude, GPS speed, heading, accuracy and altitude
- Battery/charging, connection type, model, Android version where available
- Visible Android foreground-service notification during continuous tracking
- Moving/stopped/offline state
- Near-real-time latest-location updates using Supabase Realtime
- Route history and movement-derived trips
- Distance, duration, average speed and maximum speed
- Overspeed events with cooldown and Firebase push alerts
- Circular geofences with enter/exit alerts
- Tracker online/offline alerts
- Failed tracking notification deliveries retry while delivery_count remains 0
- Offline telemetry queue on the tracker device (bounded to 150 points)
- Server-side invalid GPS/timestamp/speed-spike filtering
- Admin global tracking alerts; owners only see authorized vehicles
- RLS policies on tracking data
- OBD-II provider interface prepared for a later real Bluetooth adapter

## 1. Supabase database

Open Supabase SQL Editor and first run:

1. `supabase/GPS_TRACKING_RUN_THIS.sql`

The same schema is also included as the migration
`supabase/migrations/20260816_gps_tracking.sql`.

High-frequency route points are stored once in `vehicle_locations` using the
`trip_id` column; there is no second duplicate trip-point write. Trip summaries
remain in `vehicle_trips`. The supplied retention job keeps raw route telemetry
for 90 days by default while retaining speed/geofence/audit events for 730 days.

## 2. Deploy GPS Edge Functions

From the Flutter project root:

```cmd
powershell -ExecutionPolicy Bypass -File scripts\deploy_gps_tracking.ps1 -ProjectRef ssykwhwnujxkzokpdeey
```

Functions:

- `vehicle-tracking-pair`
- `ingest-vehicle-telemetry`
- `check-tracking-offline`

Then return to Supabase SQL Editor and run:

2. `supabase/GPS_TRACKING_SCHEDULE_RUN_THIS.sql`
3. `supabase/VERIFY_GPS_TRACKING.sql`

The scheduler uses the existing `CRON_SECRET` / Vault secret
`insuredrive_cron_secret`, checks tracker offline state every five minutes, and
runs the bounded telemetry-retention cleanup daily.

All three functions have gateway JWT verification disabled in `supabase/config.toml`
because the handlers perform their own validation. Pairing/telemetry validate
the current signed-in user; telemetry additionally validates the per-device
secret. The scheduled health check validates `x-cron-secret`.

## 3. Android project

Fresh ZIP extract:

```cmd
scripts\prepare_android_release.bat
dart pub global run flutterfire_cli:flutterfire configure --project=insureapp-49598
flutter pub get
```

Choose `android` and `web` in FlutterFire and overwrite the template
`lib/firebase_options.dart` when asked.

The Android preparation script adds the required location/foreground-service,
network, wake-lock and notification permissions. GPS hardware is marked
`required=false`, so the app can still install on a device without GPS and show
that tracking is unavailable.

Build:

```cmd
scripts\fix_android_build_and_build_apk.bat
```

## 4. Pair a vehicle

Administrator phone/web:

1. Open **Vehicles** or **Live Tracking**.
2. Open a vehicle -> **GPS Tracking**.
3. Select **Pair Device**.
4. A temporary code and QR payload are generated.

Dedicated Android car audio:

1. Install the same InsureDrive APK.
2. Sign in as the assigned vehicle owner or an Administrator.
3. Open **Vehicle Tracker Mode**.
4. Enter the temporary pairing code.
5. Device name can be changed; a dedicated Gmail address is optional metadata.
6. Allow precise location and notifications.
7. Press **Start Tracking**.

Continuous tracking is never hidden: Android shows a persistent foreground
notification while the location stream is active.

## 5. Tracking behaviour

Defaults per vehicle:

- moving threshold: 5 km/h
- moving upload interval: about 7 seconds
- stopped upload interval: 60 seconds
- tracker offline threshold: 180 seconds
- speed alert limit: 80 km/h
- overspeed cooldown: 300 seconds
- movement-trip stop threshold: 180 seconds

Administrators can edit key tracking settings from the vehicle GPS page.

## 6. Live Tracking

The Admin/Owner navigation includes **Live Tracking**.

Admin sees authorized fleet summary:

- Total Vehicles
- Online
- Moving
- Stopped
- Offline
- Overspeed Today

Vehicle cards show owner, speed, latest coordinates/time and tracker status.
Selecting a vehicle opens a map and its tracking details.

## 7. Trip and event history

Vehicle **Trip History** provides a date filter and event filter for:

- trips/routes
- overspeed events
- geofence events
- tracker online/offline events

Trips are explicitly labelled `movement` unless a future real OBD/ignition
source is implemented. GPS movement is not represented as ignition state.

## 8. Geofencing

Admin -> Vehicle -> GPS Tracking -> Geofences.

Create a circular zone with latitude, longitude and radius. Entry/exit events
are stored and can create FCM notifications according to the zone settings.

## 9. Security / privacy

- Never store Gmail passwords.
- Never bundle Firebase service-account JSON in the app/ZIP.
- Never put a Supabase service-role key in Flutter.
- Device secrets are stored in Android secure storage and hashed server-side.
- Unpairing revokes the device secret immediately.
- High-frequency tables are read-only to authenticated clients; Edge Functions write them.
- Owners are restricted by RLS to vehicles assigned to them; Administrators can view all.
- Tracking requires an explicitly paired device and a visible foreground notification.

## 10. Car audio requirements

The Android head unit needs:

- Android capable of running the Flutter APK
- GPS/Android Location Services for actual location tracking
- Internet through SIM, Wi-Fi or hotspot to upload in near real time
- permission to run the foreground tracking service

If GPS hardware/services are unavailable, the app shows `GPS Disabled` or no
GPS fix instead of inventing a location.

## 11. Optional OBD-II

`lib/services/obd_service.dart` defines the future integration boundary. The
current build does not invent RPM, coolant, engine load, DTCs or ignition data.
Those values should only be exposed after a real supported Bluetooth OBD-II
adapter is implemented and connected.
